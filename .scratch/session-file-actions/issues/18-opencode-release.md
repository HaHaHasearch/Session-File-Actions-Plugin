## 交付结果

用同一候选提交生成的 OpenCode 插件包独立完成安装、功能和兼容性验收。

依据：[§1.1](../../../doc/会话附件操作插件需求Spec.md#11-最终交付物与完成条件)、[§1.2](../../../doc/会话附件操作插件需求Spec.md#12-windows-插件安装说明)、[§5](../../../doc/会话附件操作插件需求Spec.md#5-两个宿主分别验收)、[§5.1](../../../doc/会话附件操作插件需求Spec.md#51-验收用例与附件来源)。对应验收用例 01–14（OpenCode 两列）。

## 验收条件

- [ ] 在干净 Windows 配置验证按精确包名安装、解压目录加载、GUI 启用、升级、回退与卸载；不覆盖用户已有配置。
- [ ] 按 §5.1 分列路径与内容，覆盖历史消息、持久媒体、内联字节和远端，同宿主混选；记录版本、包哈希、粘贴哈希、失败与未验证组合。
- [ ] 交付含 ./gui-experimental 预构建入口的 npm 包、安装说明、最低实测版本及兼容表。依赖补丁时交付匹配验证构建与可重建依据；核验发布身份后走授权发布流程。

## 分支、提交与合入

从两端约定的同一 `windows-one` 候选提交开 `opencode-release`，记录候选提交号与包哈希。

按可验证行为提交，相关实现、测试和必要文档同次提交。提交或 PR 标题示例：`chore(opencode): verify Windows release package`。合回 `windows-one` 前同步集成分支，复跑本票及受共享契约影响的验证。在 Comments 记录实际提交号、验证结果和证据位置。

两端分别验收。修复改变候选产物时记录新候选并复验受影响端；修改共享代码需重新构建、复验两端。两端正式支持组合通过后才将经过验收的集成版本合入 `main`。仅验证构建通过或必要项尚未验证时保留交付缺口。
