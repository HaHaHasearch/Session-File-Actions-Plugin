## 1. 产品目标与边界

让用户像在资源管理器里操作文件一样，直接在聊天消息里的附件卡片上复制、打开或保存文件。最重要的体验是鼠标停在一份报告上按 `Ctrl+C`，切到资源管理器按 `Ctrl+V`，就得到这份报告。右键「复制文件」提供相同能力。接收窗口支持文件粘贴时，用户也可以直接把报告作为邮件或聊天附件。

第二个场景是收集同一次对话的交付物。假设第一条消息里有报告，第三条和第五条消息里各有一张表，用户可以跨消息选中这三个附件，一次复制，或选一次目录保存。选择只在当前会话生效。

所有入口都依附于现有附件卡片。独立文件管理页面、跨会话多选、统一文件库、预览中心、版本比较和 AI 分类搜索均在本期范围之外。两个客户端分别安装和验收，面向用户的操作语义一致。

## 2. 功能基线

下表沿用原会话最终清单的功能编号。单文件「另存为」也在已确认的卡片菜单设计中。

| 编号 | 用户操作 | 预期结果 |
|---|---|---|
| F01 | 悬停附件 | 在原卡片上显示轻量入口，例如「复制文件」「另存为」「更多」。 |
| F02 | 右键普通文件附件 | 在当前消息中打开文件菜单，按操作对象数量展示适用命令。 |
| F03 | 选择「复制文件」 | 把源附件作为 Windows 文件放入剪贴板。粘贴后保留原名和原始字节，包括二进制内容。 |
| F04 | 悬停附件并按 Ctrl+C | 与菜单调用同一复制动作，遵循第 3 节的快捷键优先级。 |
| F05 | 在当前会话中用 Ctrl / Shift 选择 | 支持跨消息增减选择和连续区间选择，能看出哪些附件已选中。 |
| F06 | 复制多个选中附件 | 一次复制整个集合，一次粘贴可取得全部文件。 |
| F07 | 另存为 | 单文件可指定保存位置和名称。多文件只选择一次目录，各文件按原名平铺保存，重名时保留两份。 |
| F08 | 批量导出到指定目录 | 将选中集合导出至用户选定的目录，显示各项结果。额外的目录组织规则见第 4 节。 |
| F09 | 打开文件 | 以 Windows 默认关联程序打开当前附件对应的文件。 |
| F10 | 打开方式 | 让用户为当前文件选择应用。 |
| F11 | 在资源管理器中定位 | 打开当前附件实际所在的本地目录并选中该文件。 |
| F12 | 复制文件路径 | 复制实际可用的本地路径文本。多选时每个文件一行，与 F03 的文件粘贴操作可明确区分。 |

「复制文件内容」曾作为单个文本附件的补充菜单项提出，未列入最终 F01–F12 清单，保留为待确认项。

## 3. 附件卡片与快捷键

右键已选附件时保留整个选择集合；右键未选附件时，将操作对象切换为该附件。单文件菜单提供复制、打开、打开方式、定位、另存为和复制路径。多文件菜单提供复制文件、批量另存为、批量导出和复制路径。反馈紧邻操作，例如「已复制 3 个文件，可在资源管理器中粘贴」。只有系统剪贴板写入成功后才显示复制成功。

| 操作或上下文 | 交互设计 |
|---|---|
| Ctrl + 单击 | 增加或移除一个附件，其他已选项保持选中。 |
| Shift + 单击 | 从选择锚点选到目标附件，顺序按会话消息及消息内附件排列。 |
| Ctrl+A / Esc | 在附件操作上下文中，全选当前会话可操作的附件 / 清空选择。 |
| 输入框、代码编辑器有焦点，或存在文本选区 | 宿主优先处理文本复制，即使鼠标正停在附件上。 |
| 附件操作上下文中按 Ctrl+C | 有多选集合时复制集合，否则复制悬停附件。仅有历史选择且用户已离开附件操作上下文时，快捷键交还宿主。 |
| 滚动、切换消息或重绘卡片 | 已选对象和锚点按稳定附件标识保存。虚拟滚动移除屏幕上的卡片时仍保留选择。 |
| 切换会话、刷新或卸载插件 | 清空选择和锚点。新会话即使有同名附件，也不会沿用旧选择。 |

## 4. 保存、导出与失败反馈

- **批量另存为**适合快速保存，用户选一次目录即可。若两条消息各有一个 `report.xlsx`，或目录中已有同名文件，自动分配可用名称，如 `report (2).xlsx`。任何已有文件都应保留。
- **批量导出**以用户指定的目录为目标。会话还提出了按平台、会话或文件类型建子目录、生成导出清单等整理方式。这些是候选设计，具体规则尚未确认。两种保存命令可共用写盘与重名处理逻辑。
- **长批次**采用轻量进度提示，显示已完成数和总数，允许取消剩余任务。某项保存失败时，保留已成功文件，继续处理其他项，结束时列出成功、失败、取消数量，以及失败文件和原因。
- **批量复制**需要一次发布整个文件列表。建议先准备好所有选中附件，再写剪贴板。任何附件读取失败时，指出失败项并结束此次复制，保留原剪贴板内容。系统写入阶段若失败，应报告实际结果。

## 5. 技术设计与验证边界

建议采用 TypeScript 共享核心、两个独立宿主适配器和一个 Windows 文件服务。以下是会话提出的实现路线，接口名称用于指导验证。

| 模块 | 职责与候选接入方式 |
|---|---|
| 共享核心 | 管理当前会话 ID、稳定附件 ID、消息内顺序、选中集合和锚点。根据上下文决定菜单、快捷键和批量操作对象，汇总逐项结果。核心独立于界面框架。 |
| DeepSeek Harness 适配器 | 调研 Cordis / React、`ctx.contextMenus`、普通附件组件扩展点和 `FileAttachmentRef`。验证能否从被右键的卡片定位附件，并经授权取得原始字节。图片卡片上的菜单不能证明普通文件卡片也开放此能力。 |
| OpenCode Desktop 适配器 | 调研 GUI 扩展能否在原卡片取得对应的 Session Message / File Part，并读取该附件。区分桌面 UI、服务端插件和桌面主进程权限。仅注册独立查看器不足以满足 F02。 |
| Windows 文件服务 | 将授权取得的附件落盘，提供文件剪贴板、打开、定位和保存能力。会话建议验证 Rust + Win32 辅助程序，也讨论过 C# 或宿主原生接口。语言、进程生命周期和分发方式以技术验证为准。 |

### 从卡片到系统粘贴

1. 从当前卡片取得会话和附件身份，经宿主授权读取原始内容。用两个同名但内容不同的附件检验映射。禁止按显示名称搜索工作区来猜测源文件。
2. 将原始字节完整写入受控本地缓存，保留可识别的文件名并隔离同名附件。批量处理建议限制并发、大文件流式写入；按内容哈希去重是可选优化。
3. 将准备好的真实路径作为 Windows 文件列表一次写入剪贴板，候选原生格式为 `CF_HDROP`。普通路径文本只用于「复制文件路径」。原生服务仅接受经过校验的附件或受控路径。
4. 用户可延迟或连续粘贴。复制完成、切换会话和关闭插件均不能立即清除仍被剪贴板引用的文件。建议在确认引用已失效后延迟清理，具体保留周期待验证。
5. 在附件解析、读取、缓存写入、剪贴板发布和导出结果处记录操作标识、阶段、数量及错误原因。日志应能区分「附件内容未取得」与「系统剪贴板写入失败」，避免记录附件正文。

## 6. 双平台验收

以下用例在两个客户端分别执行，记录宿主版本、附件类型、实际结果和失败阶段。测试数据至少包含普通文本文件、二进制文件，以及分属不同消息的两份同名异内容文件。

| 用例 | 操作与通过条件 |
|---|---|
| 原卡片入口 | 在普通文件卡片上悬停、右键，看到相应入口。对两份同名附件分别操作，各自取得正确内容。 |
| 两种复制入口 | 分别用悬停 Ctrl+C 和右键「复制文件」，在资源管理器粘贴，核对文件名和内容哈希与对应源附件一致。 |
| 跨程序与延迟粘贴 | 在至少一个支持文件粘贴的邮件或聊天窗口得到文件附件。一次复制后切换会话、再次粘贴仍可读取文件。 |
| 快捷键共存 | 在输入框、代码编辑器和消息文本选区中复制，得到选中的文本。在附件上下文多选后复制，得到完整文件集合。 |
| 跨消息选择 | 用 Ctrl 增减、用 Shift 跨消息选择连续附件，滚动后右键已选项仍作用于整个集合。右键未选项只作用于该项。 |
| 保存与导出 | 分别执行单文件另存为、批量另存为、导出到指定目录。核对目录、数量和字节内容。批量操作各选一次目录，已有同名文件完好。 |
| 系统菜单 | 默认打开、选择打开方式、资源管理器定位均针对同一份正确附件。复制路径后，粘贴所得文本可定位该文件。 |
| 失败与取消 | 制造单项不可读或目标目录不可写。操作显示失败文件和阶段，保存批次保留成功项。复制批次缺失源文件时不提示成功。取消导出后结果可核对。 |
| 生命周期 | 切换会话、刷新、卸载后重新进入，选择已清空。验证缓存清理不会破坏剪贴板里仍有效的文件引用。 |

## 7. 开发顺序与待决事项

先做三个小验证，再决定正式实现。**Harness 和 OpenCode 各做一个普通附件卡片验证**，证明可通过受支持的扩展点绑定右键，并从该卡片取回正确的原始附件。**Windows 单独做文件复制验证**，在资源管理器及另一款支持文件粘贴的程序中实测单文件、多文件和延迟粘贴。每个验证独立记录结果。

验证通过后，实现共享的选择与批量操作逻辑，分别接入两个客户端，再执行第 6 节的完整验收。如某宿主缺少普通附件扩展点或授权读取接口，记录宿主版本、缺失能力及受影响功能，单独评审接入方式。独立页面不能计作原卡片交互验收通过。

进入实现前仍需确定的细节包括批量导出的目录组织规则、是否提供「复制文本内容」，以及确保延迟粘贴可用的缓存清理策略。本稿未对宿主 API 或系统剪贴板完成实测。
