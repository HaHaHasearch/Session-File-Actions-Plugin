# 会话附件操作插件｜程序架构与项目目录规划

状态为实施前设计。当前可以确定模块职责、依赖方向和仓库归属；宿主扩展签名和二进制传输方式待 P0 用打包后的宿主验证。功能以[需求文档](./会话附件操作插件需求Spec.md)为准，工具链、宿主提交和 P0–P4 放行条件见[技术路线](./会话附件操作插件技术路线.md)。

## 1. 四个模块，两份插件

| 模块 | 职责 | 运行位置与依赖 |
|---|---|---|
| `core` | 用出现位置区分附件，按消息顺序维护选择与锚点，根据选择数量、版本语义和可用能力计算动作，描述批次结果。 | 普通 TypeScript。适配器传入有序附件和交互上下文。核心不读 DOM、磁盘或网络。 |
| `desktop-files` | 将授权字节写入本机，校验并管理临时副本，发布文件剪贴板，安全地另存为。 | 用户电脑的 Electron main。使用 Node 和 Electron，只接收可信宿主适配代码提供的数据。可引用核心结果类型。 |
| `harness-plugin` | 在 Cordis / React 侧连接原卡片与菜单，从会话消息或交付记录解析来源，通过 Harness 桌面桥请求本地动作。 | 客户端依赖 core；Host 侧使用 Harness 文件与附件服务。preload 与 main 的改动归 Harness 宿主仓库，main 接入 desktop-files。 |
| `opencode-plugin` | 在 Solid GUI 侧连接原卡片、菜单和选择；插件 main 连接本机文件操作，按消息所属服务器解析数据。 | GUI 侧依赖 core，main 侧使用 desktop-files。卡片扩展点归 OpenCode 宿主仓库。 |

窗口代码只能调用各宿主声明的桥接方法。两个插件不相互导入，也不从本机上游克隆的相对路径引入运行时模块。core 和 desktop-files 是内部模块，随相应构建产物交付。Harness 验证版需要把 main 侧实现纳入其桌面构建；OpenCode 则可以将实现纳入 GUI 包的 main 入口。两端能否在目标安装版加载这些能力，按版本分别记录。

### 1.1 运行时架构

```text
宿主窗口：Harness / React 或 OpenCode / Solid
  原卡片 → 宿主适配器 → core 计算选择和可用动作
                  ↓ 用户触发动作，冻结目标集合
桌面主进程：宿主适配器的可信操作入口
  绑定发起窗口、会话、服务器与操作 ID
        ├── 向文件所属 Host 请求解析与授权读取
        │      Host 查消息或交付记录 → 返回版本、名称及受权内容
        └── 将内容交给 desktop-files
               在本机准备文件 → 校验 → 写剪贴板 / 另存为 / 系统打开
                  ↓ 返回操作 ID、阶段与逐项结果
发起窗口：仅向仍对应此次操作的界面展示结果
```

这里的 Host 是拥有会话及文件访问权限的一方，可以在远端。桌面主进程运行在用户的 Windows 电脑上。两者即使部署在同一台机器，也要保留会话授权这一步。UI 可以决定显示哪些菜单项，实际执行时由可信入口重新检查动作与来源是否匹配。已有宿主动作如果已经具备相同授权和版本语义，可直接调用。

### 1.2 三个关键对象

| 对象 | 所有者与生命周期 | 约束 |
|---|---|---|
| 附件出现位置 | 宿主产生；窗口在当前会话内用它选择卡片。包含服务器或宿主实例、会话、持久消息或事件、项标识或稳定序号。 | 同名附件、同一份内容被发送两次，都能独立选中。列表下标、显示名称、DOM 节点和磁盘路径都不足以单独标识它。 |
| 已解析来源 | Host 在执行操作时从持久记录生成，受本次操作的权限和取消信号约束。 | 明确区分“发送时原件”“路径当前版本”和“不可用”。声明预计长度及已知摘要。客户端传来的名称、路径或哈希不能作为读取授权。 |
| 本机文件副本 | desktop-files 在用户私有目录管理，记录用途和归属。 | 剪贴板副本保留到解除引用并经过清理宽限期；编辑器可打开单独的可编辑副本。用户选择目录中已成功保存的文件归用户管理。 |

### 1.3 模块间如何调用

以下是调用者应能依赖的行为，字段拼写和传输协议在宿主验证后确定。

| 调用 | 输入与返回 | 谁保证什么 |
|---|---|---|
| 计算动作（窗口内） | 有序出现位置、当前选择、右键或悬停目标、焦点与文本选区 → 动作及目标集合 | core 保证右键与快捷键遵循同一套选择规则。适配器负责提供真实的焦点与宿主能力；文本复制优先时直接将事件留给宿主。 |
| 执行动作（窗口 → 桌面） | 操作 ID、动作、冻结的出现位置 → 本次操作结果 | 桌面从可信 IPC 上下文绑定窗口身份，核验会话和允许的动作。保存目录由本机对话框选择。窗口不能借此指定任意来源路径、剪贴板格式或命令。 |
| 读取选中附件（桌面适配器 → Host） | 绑定的会话、出现位置 → 已授权内容或具体失败 | Host 按记录读取并校验。有明确路径时读取当前文件，路径失效须报错。大文件支持逐块读取和取消。 |
| 执行本机文件动作（桌面内部） | 已解析来源、授权数据通道、动作及取消信号 → 逐项完成情况和整体结果 | desktop-files 负责隔离同名副本、完整性校验、临时文件清理和系统写入。只有实际发布成功的文件才进入成功计数。 |

### 1.4 状态、并发与失败

- **选择状态**属于窗口里的活动会话。切换会话即清空选择和锚点。已经发起的操作持有原选择快照，后续点击不能改变其文件。结果按操作 ID 返回原上下文，不能显示成新会话的操作结果。
- **复制**依次经过接收、解析、准备和发布。任一项准备失败或发布前被取消，整批结束并清理本次未发布副本。桌面主进程对本宿主发起的剪贴板写入排序：较新的复制已获受理时，仍在准备的旧操作不能在其后覆盖剪贴板。这个保证仅限本宿主进程，其他 Windows 应用可以随时改写系统剪贴板。
- **另存为**对每个文件单独准备、校验和发布。磁盘满、远端断连或取消时，分别列出已成功、失败及未执行项。对话框被关闭属于用户取消。重复点击同一次请求时按操作 ID 合并进行中的工作，显式再次发起的动作使用新 ID。
- **确认与恢复**以实际副作用为准。系统写入前的失败可明确报告未发布；若进程在系统调用与回执之间断开，返回或在重连时提示“结果未确认”，不自动重放复制或另存为。日志用操作 ID 串联解析、准备、校验、发布各阶段。重启后只清理已确认归属且可回收的临时文件。

## 2. 一次跨消息复制怎样执行

假设同一次会话中有两份同名报告。用户 Ctrl 单击选中两份，然后右键其中一张已选卡片，在菜单中选择「复制 2 个文件」。

1. **窗口固定操作对象。** 适配器取得当前宿主实例、会话、持久消息或交付事件，以及附件在其中的位置。core 输出一份有序选择快照。重绘和虚拟滚动不改变快照；内容哈希只用于完整性校验，相同内容出现两次仍是两个选择项。
2. **Host 核实来源和版本。** 请求包含操作 ID、动作和出现位置。Host 验证当前窗口有权访问该会话，并从持久记录重新解析每一项。Harness 上传附件读取保存的原件；Harness 交付路径和 OpenCode 旧路径引用读取当前文件。混选按项解析，无需确认。
3. **桌面准备本机文件。** 桌面适配器通过受权通道接收内容，将本机可读的数据流交给 desktop-files。远端路径始终由所属 Host 解释。具体桥接协议可采用按块传输或受控流句柄；P0 必须验证取消、断连和大文件行为，不能假定普通 IPC 能直接序列化 Node 流。
4. **一次发布并反馈。** 所有文件准备完毕后，main 一次写入文件列表，再向发起窗口报告成功数量。准备失败时清理该次未发布副本，保留原剪贴板；系统写入失败则报告实际阶段。插件卸载时释放监听器，停止准备中的复制与剩余保存，清理本次未完成文件，保留保存成品；已提交但无回执时记录结果未确认，不重放。已发布副本单独按剪贴板引用清理。

另存为与复制共用来源解析与字节校验，完成条件不同。复制必须整批准备成功；另存为按文件发布，单项失败保留其他成功项。默认打开、打开方式与定位优先使用宿主已有动作；打开不可变上传快照时交给外部程序的是可编辑副本。

### 3.2 如何决定一个改动放在哪里

| 改动示例 | 归属与测试位置 |
|---|---|
| 两个宿主都要改变 Shift 区间选择，或右键未选项的处理规则 | 改 `packages/core/src/selection.ts` 或 `actions.ts`，测试与实现同目录，如 `selection.test.ts`。输入使用消息顺序与出现位置。 |
| Harness 普通上传卡片需要暴露附件位置，或需要新增桌面 preload 方法 | 开宿主分支修改上游卡片或桌面桥，在对应宿主包运行测试。插件侧的菜单贡献放 `plugins/harness/src/client/`，会话授权及读取放 `host/`。Host 可能运行在远端，不能在这里访问用户剪贴板。 |
| Windows 延迟粘贴时临时文件被提前清理 | 修复 `packages/desktop-files/src/local-copies.ts`，就近验证清理条件，在 `tests/windows/` 用真实剪贴板回归。目录内只提交可重复使用的合成样本或生成逻辑。 |

包之间通过清单声明的入口导入。两个插件窗口均可依赖 core；desktop-files 仅供受信任的桌面端调用；两个插件之间没有依赖。各包保存自身的 TypeScript 配置，React 与 Solid 分开设置 JSX，renderer 和 main 分开检查运行时类型。Harness 构建产物在自身 `lib/`，OpenCode GUI 产物在自身 `dist/`。开发日志、测试输出和用户文件均与版本控制中的源码隔离。

### 3.3 主仓库与上游仓库

两个 `upstream/` 子目录保持独立 Git 仓库。根工作区使用 `packages/*` 和 `plugins/*` 白名单；实施时在主仓库的 `.gitignore` 写入两个克隆的精确路径。现有本机排除规则已生效，但不会随项目分发。

宿主代码在其功能分支修改。原型首次依赖补丁时，在 `host-patches/<宿主>/README.md` 记录上游基线、可获取的补丁提交、应用步骤及匹配的插件版本；补丁尚无可获取提交时，将可应用的补丁文件放在同目录。构建依赖以这些记录为准，避免主项目只能在某台机器有未提交修改的克隆上运行。正式发布前从干净检出重建并安装两份产物。

## 4. 第一批实际要建什么

| 顺序 | 创建范围 | 判断可以继续的证据 |
|---|---|---|
| P0 桌面与卡片入口 | 建根 workspace、desktop-files 的最小剪贴板实现和 Windows 验收样本。两个上游分别开实验分支；Harness 与 OpenCode 适配器目录各自只放能从真实消息卡片取得身份的最小入口。 | 已知字节的文件能粘贴至资源管理器，名称和哈希相符。分开记录两个宿主的卡片身份、依赖的补丁和加载方式。单独运行样例不能代替宿主验证。 |
| P1 Harness 单文件 | 接通 Harness 交付卡片与用户上传附件。出现稳定的共享身份和动作规则时建立 core。 | 修改交付路径后能明确复制当前版本；上传后删除本机原件，仍能取回发送时的字节。 |
| P2–P4 多选、第二宿主与发布 | 增加 core 的跨消息选择、批量另存为和失败用例，再完善 OpenCode 媒体读取、路径读取及历史消息兼容，最后做安装包验收。 | 两宿主分别通过 有效功能项（F08 已取消）；兼容记录明确区分官方安装版和带补丁验证版。 |

目前没有必要创建空包或冻结所有接口。第一个架构决策点是 P0 能否在真实的原卡片上取得准确身份，并将有权限读取的内容送达桌面主进程。通过后再固定跨进程请求字段和长期维护的宿主补丁。
