# 会话附件操作插件｜Windows 1.0 技术路线

**实施建议，2026-11-03。** 本文对应[需求与设计 F01–F12](./会话附件操作插件需求与设计.md)。源码基线为 [DeepSeek Harness 8bd073392eef](https://github.com/deepseek-ai/deepseek-harness/tree/8bd073392eef6f54e921a093b95076248eb08cbb) 和 [OpenCode 3ba597f7769e](https://github.com/anomalyco/opencode/tree/3ba597f7769e19cc3b5f67e3d6667e7b6318f6a3)。下文的“新增”均为拟实现能力。源码核查不代表已完成运行验收。

## 1. 交付方式先定下来

**采用两个宿主适配器、一份 TypeScript 选择与批处理逻辑，以及运行在用户 Windows 桌面主进程中的文件操作代码。** 菜单和选择状态直接作用于现有消息附件卡片。第一条运行链路选 Harness 交付卡片；第一条能证明“发送后仍能取回原件”的链路选 Harness 用户上传附件。两者分开验收。

完整版本需要少量宿主改动。Harness 要让已发送普通附件的卡片发出带身份的操作事件，并补齐文件读取和桌面动作；OpenCode 要提供已发送附件的 GUI 扩展点。若要求新发送的路径型上传也能还原原件，OpenCode 还需要在接收文件时保留字节并随消息持久化引用。这项存储改动与 UI 扩展要分开评审。

| 交付对象 | 必要条件 | 可对用户承诺的范围 |
|---|---|---|
| 现有官方安装版 | 只使用当前公开插件接口 | Harness 的部分交付卡片已有扩展点。源码证据不足以支持在两个官方安装版上仅安装插件即覆盖全部需求。 |
| 固定版本验证包 | 从上述提交分别开功能分支，构建含最小扩展的宿主，安装匹配的插件 | 可端到端验证原卡片、原件和系统粘贴。验证包标注基线和补丁，使用独立测试配置。 |
| 正式版 | 上游发布所需能力后匹配其版本；若上游未接纳，则须另行决定是否维护和分发自有宿主构建 | 分别发布 Harness、OpenCode 插件并列出最低实测版本。缺少必要能力时显示具体缺项，禁止按文件名猜测或注入 DOM。 |

### 1.1 首版技术栈决策

**主语言统一为 TypeScript 6，UI 和打包方式跟随各自宿主。** 开发端采用一个 pnpm workspace 管理插件自有代码和测试。交付物为两个宿主各自加载的插件包，用户使用宿主随附的 Electron。下表中的精确版本对应本文固定的源码基线；兼容其他版本时，需要重新验证插件加载和桌面能力。

| 层级 | 本项目采用 | 职责与边界 |
|---|---|---|
| 共享核心 | TypeScript 6、严格类型检查、标准 `Map` / `Set`、`AbortSignal` | 用普通 TypeScript 模块实现选择、区间顺序、批处理取消和结果汇总。对外使用可序列化的附件身份与结果类型。React、Solid、文件系统和 Electron 调用均留在适配层。 |
| Harness 插件 | Cordis（`@deepseek-ai/cordis`）、React 18.3.1、TSX、宿主 UI primitives / slots / context menus，局部样式使用 CSS Modules | Cordis 注入会话与附件服务，React 负责原卡片交互。Host 按会话授权读取附件；桌面 renderer 经 preload 的 `contextBridge` 和用途受限的 IPC 调用 main。 |
| OpenCode 插件 | `@opencode/plugin/gui`、SolidJS 1.9.17、TSX、宿主组件与样式、插件的类型化 IPC | 窗口端用 `Plugin.define` 配置 GUI 贡献，main 端执行本机动作。需改服务端快照或协议时沿用 OpenCode 的 Effect 4.1.0、Schema、HttpApi 和生成客户端；这些依赖留在宿主边界。 |
| Windows 文件服务 | 宿主 Electron main（Harness 44.7.0，OpenCode 44.9.1），Node 内置 `fs/promises`、`stream`、`crypto`、`path`、`url` | 用流准备文件、SHA-256 校验内容、`pathToFileURL` 编码路径。Electron `ClipboardItem` 写入 `text/uri-list`，在 Windows 产生 `CF_HDROP`；文件对话框、默认打开和定位复用宿主已有实现。首版剪贴板不引入 Rust、C# 或常驻进程。 |
| 状态与持久化 | 会话内存状态、宿主附件存储、当前用户私有文件目录 | 多选仅驻留于会话内存。Harness 复用 Attachment Store；OpenCode 对已有媒体复用 SessionBlob，新路径快照按第 3 节扩展宿主已有持久化和引用生命周期。客户端剪贴板批次使用私有目录和小型本地清单，清单原子更新，文件字节保存在文件系统。首版无需插件专属数据库。 |

### 1.3 依赖管理

主仓库和两个宿主仓库分别安装、锁定和验证依赖。根工作区建立时，在 `package.json` 用 `packageManager` 固定 pnpm 版本，用 `engines.node` 声明支持的 Node 范围；`pnpm-workspace.yaml` 只纳入 `packages/*` 和 `plugins/*`。首次安装生成根 `pnpm-lock.yaml`，与工作区配置及各包清单一起纳入 Git。此后按下表复现开发环境。

| 安装位置 | 版本依据 | 干净检出与 CI 的安装命令 |
|---|---|---|
| 本项目根目录 | 本项目各包清单、根 `pnpm-lock.yaml` | `pnpm install --frozen-lockfile` |
| `upstream/deepseek-harness/` | 该提交的 `packageManager` 和 `pnpm-lock.yaml` | 在 Harness 仓库运行 `pnpm install --frozen-lockfile` |
| `upstream/opencode/` | 该提交的 `packageManager` 和 `bun.lock` | 在 OpenCode 仓库运行 `bun install --frozen-lockfile` |

**新增或删除。** 先检查宿主和标准库能否满足需求，再把依赖声明在直接使用它的包。TypeScript、Vitest 等全工作区工具放根 `devDependencies`；tsdown、Vite 等专用打包工具放对应插件的 `devDependencies`。包自身交付并在运行时使用的库放 `dependencies`。内部包通过 `workspace:*` 引用，出包时确认已内联或能由正式依赖解析。自有包直接选定的第三方构建与运行依赖使用精确版本。对于宿主提供的 React、Cordis、Solid、Electron 或 SDK 模块，按该宿主加载契约配置外置；需要对安装方声明兼容要求时用 `peerDependencies`，在本地开发依赖中固定已验证版本。Node 内置模块无需安装。

工作区建好后，例如在根目录运行 `pnpm --filter ./plugins/harness add -D --save-exact tsdown@0.22.2`，只修改 Harness 插件清单和主仓库锁文件。删除使用 `pnpm --filter ./plugins/harness remove tsdown`。清单与锁文件作为一次变更提交；冻结安装报不一致时先核对清单变动，仅在有意更新的仓库重新生成锁文件。

**升级与回退。** 一次升级一个可独立验证的依赖或一组必须配套的依赖，说明升级原因、受影响的包和锁文件变化。共享核心变更执行类型检查并运行两个适配器的相关测试；构建工具或宿主 SDK 变更要从打包产物验证加载、卸载和原卡片操作；Electron 或文件接口变更另做 Windows 真实复制与粘贴。宿主基线升级先在对应仓库分支验证，再更新主项目的兼容记录和补丁引用。检查失败时保留已验证基线；需要回退时一并还原相应清单、锁文件和宿主引用。

## 2. 附件身份与版本契约

每一项操作从用户点中的**卡片出现位置**开始。选择键由宿主实例或服务器、会话、持久消息或事件、附件在该消息中的标识或序号构成。交付卡片已有的事件序号加文件序号可直接使用。内容哈希用于校验或复用存储，不能作为选择键。相同字节在两条消息里出现两次，或分别叫两个名字，都应保留两个选择项。仅有本地回显、尚无稳定身份的卡片暂不开放文件操作。

| 用户看到的来源 | 源码中的实际记录 | 1.0 如何取文件、怎样命名操作 |
|---|---|---|
| Harness 用户上传的普通文件 | 引用包含内容 ID、保存名称、精确长度，Host 有逐块读取与最终 SHA-256 校验 | 从消息解析引用，经 Host 读取保存的原始字节。显示「复制文件」。原上传路径消失仍应可用。 |
| Harness 的 AI 交付卡片 | `present` 记录工作区路径与描述；宿主明确约定打开当前文件 | 从当次交付记录解析路径，经会话授权读取，固定本次复制的内容。显示「复制当前文件」。旧交付的发布时版本无快照可恢复；若未来要求该语义，需要在交付时另存快照。 |
| OpenCode 消息或工具结果中有内容引用的文件 | 已存媒体可按 SHA-256 读取；某些消息也有直接内联数据 | 优先从持久引用解析并校验，有可信内联原始字节时直接导出。只在实际文件卡片上提供动作。媒体缺失的占位文本、预览图和 Markdown 中的同名链接都不能充当原件。 |
| OpenCode 新上传、模型以路径读取的文件 | 现有客户端可保存本地路径，或先将文件传至远端临时目录再保存路径 | 新增会话附件快照引用，保存用户提交的那份字节；保留模型原有路径输入。此改动上线后，新消息才可承诺按发送版本复制。 |
| OpenCode 历史路径附件 | 老消息可能只有名称、类型和路径 | 明示「仅有路径引用」，按需提供「复制当前文件」。远端文件经原服务器授权读取。文件已删或无权限时给出原因。严格要求原件的操作显示不可用。 |

Harness 图片有独立渲染槽和读取契约。对于图片，保留已有预览和「复制图片」，另设「复制文件」写入文件对象，仅对能取回原始字节的来源启用。同批若混有历史路径引用，不得把整批标作原件；列出受限项，让用户明确选择当前版本或调整选择后重试。[Harness 附件结构](../upstream/deepseek-harness/packages/attachment/attachment/src/types.ts) · [交付文件契约](../upstream/deepseek-harness/packages/deliverables/tool-present/README.md) · [OpenCode 上传分流](../upstream/opencode/packages/app/src/composer/attachments/attachments.ts) · [OpenCode 缺失媒体处理](../upstream/opencode/packages/core/src/session/blob.ts)

## 3. 两个宿主的具体接入

### DeepSeek Harness

1. **交付文件。** 从 `Deliverables.tsx` 沿用现有 `getTriggerProps`、`deliverables.file.actions`、原生打开和另存为。现在通用 file 菜单传递会话与路径，而卡片自身掌握 `seq/index`。为附件动作传入出现位置，避免在其他工作区菜单上误加批量操作，也能区分两次交付同一路径。右键和悬停共用同一动作。
2. **已发送的用户文件。** 在 `MessageItem → UserContent` 保留现有渲染与交互，新增可选的普通文件卡片动作绑定，将所属消息身份、附件序号和会话传入。沿用 `ctx.contextMenus` 的贡献机制；保留图片槽、文本气泡和原本的单击行为。插件未安装时普通消息照常显示。
3. **Host 读取。** 增加会话范围内的附件导出操作。由 Host 用消息身份和序号解析真实 `FileAttachmentRef`，核验当前调用方、会话归属和可读性，再调用 `readFileStream`。临时文件只有在流结束、长度与哈希验证均成功后才可发布。已有 `readAttachment` 是图片接口，其调用方和返回类型继续维持原有语义。对工作区交付物则走会话文件权限与交付记录。远端 Host 应以受权字节流返回给桌面，不能直接返回一个 Windows 无法使用的远端路径。
4. **桌面桥。** 在现有 `preload-app / ipc / file-actions` 增加用途受限的文件操作，通过可信窗口和绑定当前会话的短期句柄跨进程。沿用已有的窗口来源检查和命名规则。拖放代码的临时文件总量限制为 64 MiB，已使用文件默认保留 60 秒，两者都不适合作为剪贴板文件的生命周期；只复用适用的校验和准备逻辑。

### OpenCode Desktop

1. **卡片。** 在 `session-ui` 的已发送消息渲染处为路径引用和内容附件分别传入统一的动作上下文，由 app 接入 GUI 插件注册表。保留宿主卡片、预览和键盘激活。共享的 `AttachmentCard` 也供评论和编辑器使用，因此扩展应由消息调用方显式启用。工具结果如有独立文件卡片，应按同一接口逐类绑定和验收；普通文本路径链接不自动升级为附件。
2. **插件。** 使用 `./gui-experimental` 的窗口端贡献菜单和悬停操作，主进程端执行本机文件操作。renderer 通过声明的 IPC 契约提交操作和出现位置；main 重新绑定到可信会话解析。公开 `SlotMap` 目前未包含消息附件，单独注册 `FileViewer` 无法满足入口要求。
3. **已有媒体。** 服务端核实选中消息或工具项引用对应内容后读取。已有 `experimental.media.get` 检查持久引用并返回整个字节数组，可用于大小受控的已有媒体；它本身不证明该哈希属于当前选中的消息。大文件路径新增流式导出，避免经 renderer 转换为 Base64 或整份 Blob。远端请求使用当前服务器的认证和工作区上下文。
4. **新上传快照。** 在 composer 仍持有用户所选 `File` 时接入快照准备，重用已经保存的内容；路径型文件从同一输入流生成内容哈希、长度和受管副本。远端暂存时可由服务端对同一次上传同时生成快照和工具使用的路径。新消息的附件元数据增加可选快照引用，引用和消息一并提交；不要在发送后重新打开原路径补快照。取消、发送失败或重试产生的未引用对象可回收；消息删除、分叉和共享同一对象时按真实引用保留。现有媒体存储是否能承载目标文件大小要测量；大文件采用流式对象文件加持久引用，避免把所有普通文件塞入当前整块内存读取链路。
5. **兼容。** 旧消息无新字段时按第 2 节归类。只对已验证有能力的 server 开启新快照功能。旧 server、快照失败、超过配额均须在发送前给出可理解的状态，允许取消或明确选择宿主原有的路径发送行为。模型收到的提示、工具路径和原有消息重放不应因增加导出引用而变化。涉及公共协议时按仓库要求重新生成客户端，验证本地与远端的版本组合。

## 4. 共享操作与 Windows 实现

**一次操作的边界**：捕获当前选择 → 宿主按会话解析每个出现位置和版本 → 取得授权字节 → 准备本机文件 → 执行用户选定动作 → 返回逐项结果。共享核心只处理顺序、选择、操作对象和结果；鉴权、数据读取、UI 框架和 Electron 调用留在各自拥有该能力的一侧。初期按模块组织，无需先建独立守护进程。

| 需求 | 实施规则 |
|---|---|
| F01、F02、F04、F05 卡片与多选 | 按会话消息与附件顺序建立可操作项索引，虚拟滚动卸载卡片不清空选中项。Ctrl 增减，Shift 从锚点选择区间。跨越尚未加载的历史时先从宿主加载区间；无法取得完整顺序时给出提示。Ctrl+A 仅在附件交互上下文中选择该会话可操作附件。右键选中项保留集合，右键未选项仅作用于该项。Esc、切换会话、刷新和卸载清理选择。 |
| F03、F04、F06 复制文件 | 菜单和快捷键共用一个入口。输入框、编辑器、文本选区优先。其余仅在附件交互上下文处理 Ctrl+C，多选优先于悬停单项。全部文件准备成功后一次写入系统剪贴板。异步操作记录序号，慢操作不得在较新的复制已发布后覆盖它。 |
| F07、F08 保存与导出 | 单文件弹出保存对话框，多文件只选一次目录。首版两种批量命令共用写入实现，按原名平铺，导出可查看逐文件结果；分类子目录待产品另定。顺序流式处理即可。目标目录中先写独占临时文件，校验成功后以拒绝覆盖的方式发布；同名竞争时分配下一个可用名称。取消只清理本次未完成文件，保留已成功项。 |
| F09、F10、F11 打开、打开方式、定位 | 沿用宿主已有的系统打开、已安装应用选择和定位能力。上传快照或远端文件先物化为本机副本，打开或定位该副本；界面说明其位置。工作区当前文件可定位授权原位置。Windows 应用选择需实测至少一种已安装应用打开 Office 或 PDF 文件；若要求完整的系统“打开方式”对话框，单独接 Windows Shell 的应用选择能力。 |
| F12 复制路径 | 使用已解析且真实存在的本地路径，多项逐行写入纯文本。远端来源的本地副本标明用途。对已复制的副本路径采用有说明的保留策略；用户需要永久位置时通过另存为取得。 |

**剪贴板写入。** 在 Electron 主进程内，用 Node 的 `pathToFileURL` 为每个已验证的绝对路径生成 URI，以 CRLF 连接，在一个 Electron `ClipboardItem` 中固定写入 `text/uri-list`，等待 `clipboard.write([item])` 成功。两个基线版本的官方文档均明确此格式在 Windows 映射为 `CF_HDROP`。无需为此先写 Rust 程序。不要把 renderer 提供的任意 MIME、命令、URL 或磁盘路径原样交给 main。[Electron 44.7.0](https://github.com/electron/electron/blob/v44.7.0/docs/api/clipboard-item.md#files-the-texturi-list-mime-type) · [Electron 44.9.1](https://github.com/electron/electron/blob/v44.9.1/docs/api/clipboard-item.md#files-the-texturi-list-mime-type)

**文件保留。** 区分会话快照、可回收的剪贴板副本和用户导出文件。快照随消息引用保留；剪贴板用独立的应用私有批次目录；用户导出文件由用户管理。共享快照不能直接交给外部编辑器写入。剪贴板副本沿用原名，批内若 Windows 名称冲突则使用可辨认后缀并反馈名称映射。文件名仅取安全叶名，处理路径穿越、设备保留名、大小写和尾点空格。部分写入和取消不得产生可误用的成品。

**清理与异常。** 持久记录插件所有的临时批次。进程退出不清理已发布且可能仍被引用的副本。重启或定期清理时读取当前剪贴板，对仍被引用的批次续留；读取失败时延后清理，确认解除引用后再经过宽限期回收。容量不足先回收可回收项，仍不足则报告所需空间。剪贴板写入前的读取失败不会改变原剪贴板；系统写入自身失败只报告实际结果。日志使用操作 ID、宿主、来源种类、阶段、字节数和错误码，用户可据此区分过期引用、权限拒绝、内容损坏、磁盘满与剪贴板占用。普通日志不记录文件内容、凭据或完整私人路径。

验收记录应分别列出官方原版、带补丁验证版和正式支持版本。首版最小可演示成果是“从原卡片复制到另一款 Windows 应用”，正式完成条件是两个目标客户端各自通过适用来源和 F01–F12 的验收。本文未实施宿主改动，也未把官方合并、插件分发或桌面实测视为已完成事项。
